一句话结论

RuntimeHelpers.PrepareMethod 不读任何 m_invocationFlags（无条件强制 JIT）；HookInfo 的「清 0x80 设 0x20(mdcStatic)」位手术影响的是 CLR 原生侧 TryGetMultiCallableAddrOfCode/MayHaveNativeCode/MayBeRemotingIntercepted 对 MethodDesc+6 字节的判定分支；取真实函数头靠 md + ReadInt32(md+8) + 8 偏移跟随，不靠手术。

2026-09-10 重大更新（x86 4.8.1 9181 实锤）：手术的真正作用在 x86 上复现成功——Chanjet FastCGI 环境（System.dll IL 副本）中，MD+6 从 0x80 改为 0x20 后 PrepareMethod 会真 JIT（A/B 对比：+3 0x0B→0x39、md+8 回填 code-8、CodeAddr 真实函数头 vs 不手术仅登记不 JIT）。机制：MD+6 的 0x80 位（RequiresInheritanceCheck）使 PrepareMethodDesc 管线拦住 0x80 方法（只登记不 JIT），0x20（mdcStatic）方法则被 ExecuteGate 放行真 JIT。顺序约束：手术必须在首次 PrepareMethod 之前。 servicing 差异：9181 拦 0x80，9337+ 实测不拦（不手术也 JIT）——详见第六章。

二、CLR 逆向结论（clr.dll 4.8.4795 x64，IDA 已加 22 条注释）

2.1 PrepareMethod（FCall，0x18065eca0）—— 与 InvocationFlags 无关

  • 全程不读 mscorlib 侧 m_invocationFlags —— 那是托管对象（RuntimeMethodInfo）上的字段，native FCall 只持有 MethodDesc*，物理上无法读到
  • 无条件执行（内部 CER 检查去重），不存在"根据 InvocationFlags 跳过"的分支

2.2 m_invocationFlags 是纯托管概念

侧 位置 作用
mscorlib 托管 RuntimeMethodInfo.m_invocationFlags 字段 MethodInfo.Invoke 的准入校验缓存（NoInvoke/ContainsStackPointers → 抛异常）
clr.dll 原生 不存在 grep 全部 VM 代码零命中

托管 get_InvocationFlags IL 结构（net48 实测反汇编）：读 m_invocationFlags 字段 → 测 INITIALIZED 位 → 未初始化则懒计算（GetSecurityFlags + 逐位 OR）→ 写回缓存。消费者：InvokeArgumentsCheck/UnsafeInvoke/RuntimeConstructorInfo。与 JIT 准备无关。

2.3 真正消费 MethodDesc+6 字节的函数（★ = 手术影响点）

一句话总结分支语义：

  • ⑤ FCall → 直达 C++ 实现
  • ⑥ 已 JIT 无 precode → 直达 native code（Hook 最理想）
  • ⑦ 已 JIT 有 precode → 稳定入口（可能 E8/E9 跳板，需 HookInfo 的 md+8 跟随）
  • ⑧⑨ 未 JIT / 异常场景 → precode / 临时入口（Hook 不能直接 patch 这里）

三、md+8 语义与真实函数头获取（复现定案）

3.1 md+8（int32）= 真实 JIT 代码相对 MethodDesc 的偏移

实测（ReproMd8Probe）：StartWithShellExecuteEx md+8=0x82FEE0，md+0x82FEE0+8 = 0x7FF9A2F96A50 → 55 41 56 57（真实函数头）✓

HookInfo.Initialize() 的 E9/E8 跟随逻辑就是这个：Value = ReadInt32(md+8); Value = md + Value + 8，任何入口形态下都能拿到真实代码。

3.2 PrepareMethod 前后 entry 对比（无手术对照）

阶段 entry 形态
反射刚拿到（未 JIT） 0x7FF94A550718 E8 93 DE 7C 5F → clr.dll+0x18E5B0（PrecodeFixupThunk）
GetParameters 后 同上 无变化
PrepareMethod 后 0x7FF94A44D080 E9 63 C9 EF FF → 0x7FF94A44D080，bytes=48 83 EC 28 真实函数头

普通 PrepareMethod 就能让 entry 从 E8 回填成 E9 直达真实代码 —— 手术对这批样本非必需。

3.3 E8 跳板目标 = PrecodeFixupThunk

entry+5+rel32 = clr.dll+0x18E5B0（共享 PrecodeFixupThunk，所有未 JIT 方法指向同一地址）。GetJitFunPtrStatus 的 Injected 判定（b1 == 0xe9 || 0xe8）捕捉的就是这种形态。

4.3 触发条件的真实语义

nOffsetPre8 < 0xFF（有符号 int32 比较）：

  • Process.Start md+8=0xA2F97230 → 负数 → 恒 < 0xFF → 手术触发 ✓（此时方法已 JIT，entry=真实函数头，手术前后无变化）
  • StartWithShellExecuteEx md+8=0x82FEE0 → 正数且 ≥ 0xFF → 不触发
  • 未 JIT 方法 md+8 是小 offset（如 ReproDerived.Compute md+8=0）→ 触发检查

4.4 实验环境注意

  • WSL interop 会把 32 位 exe 拉成 64 位宿主 → x86 验证必须 Windows 侧 run-net48-x86.bat
  • x86 进程下手术分支不走（!Is64BitProcess 只裸 PrepareMethod）；x86 的 md+8 是 m_codeOrIL 指针（大值）
  • MEMORY_BASIC_INFORMATION x64 布局：RegionSize 必须 UIntPtr 且 8 字节对齐（+24），否则 VirtualQuery 全误判

五、当年为什么加 mdcStatic —— 结论（2026-09-10 已实锤，见第六章）

  1. 不是"PrepareMethod 通过 m_invocationFlags 判断是否执行"——PrepareMethod 无条件执行
  2. 不是"让 GetFunctionPointer 返回真实函数头"——x64 普通 PrepareMethod 就能回填（E8→E9）
  3. 已实锤的真实作用（x86 4.8.1 9181，第六章）：MD+6 的分类位决定 prepare 管线分流——0x80（继承检查）方法只登记不 JIT（等首次调用激活），0x20（mdcStatic）方法在 PrepareMethod 内部直接 JIT。手术 = 把方法从保守登记路径切到 JIT 路径。x64 的对应消费点在 GetFunctionPointer 决策链（MayHaveNativeCode），x86 的消费点在 PrepareMethodDesc 管线（ExecuteGate）
  4. 生产取头路径：Initialize() 的 md + ReadInt32(md+8) + 8 偏移跟随仍是主力；手术是让 PrepareMethod 真正生效的前置条件（x86 场景必需）

八、x86 4.8.1（9181）实锤：手术如何让 PrepareMethod 真 JIT

本章环境：Chanjet.TP.WebServer.FastCgi.exe（Nginx 反代 32 位 FastCGI 自宿主），CLR 4.8.9181.0 x86，System.dll 以 per-domain IL 副本加载（非 NGEN）。IDA 逆向对象：该环境 clr.dll（已标注 13 个函数）。

8.1 一个前置问题：为什么 v4.0.30319 的 clr.dll 下载不到 PDB

msdl（https://msdl.microsoft.com/download/symbols）只托管微软公开发布的二进制对应 PDB，索引以 PE 内嵌的 GUID+age 为准。下载不到只有三种可能：

  1. 非公开构建：内部重编/实验版/非 shipping 版本不在公开符号服务上（chk/retail 内部号）；
  2. 公开但有条件：Win11 24H2/25H2 起 .NET Framework servicing 的符号改为随 Windows 更新分发，msdl 镜像滞后或只对部分 build 发布（实测本机 9337 GUID 直 404）；
  3. GUID 输错：PDB 目录里取的 GUID 大小写/age 拼接错（正确格式 {32位大写HEX}{age十进制}）。

排查口诀：!lmi clr（windbg，看 Symbol Type 与 PDB 路径）→ !sym noisy + .reload /f clr.dll（看 sym srv 实际请求 URL 与响应码）。本机 9337 即第 2 类（404）；若 dump 里的 9181 能被 windbg 解析，说明 9181 在 msdl 有（或符号来自本地缓存/内部符号服务器）。

8.3 x86 9181 PrepareMethod 完整调用流

分流本质：MD+6 的 classification 字节决定方法在 gate 链中的命运。0x80（mdcRequiresInheritanceCheck，方法在 override 链上）→ CLR 无法保证继承解析完成前 JIT 的代码不作废 → prepare 管线对它只挂账（+3 停在 0x0B、md+8 保持 0），等首次真实调用走常规 PreStubWorker 激活。0x20（mdcStatic，「无继承解析需求」）→ gate 全放行 → ExecuteGate 立即 JIT 并回填。

judge/gate 的消费位（指令级）：judge1 = [MD+3]&4==0 + 协同谓词；judge2 与 ClsCmpGate = [MD+6]&7（低 3 位分类：0=IL）。0x20/0x80 高位不经这些点——分流发生在 gate 群内部的分散检查与 ExecuteGate 的 vtable 目标选择（详见 IDA 标注：PrepareMethodDesc 及其调用链 8 处注释）。

8.4 与 9337 的 servicing 差异（行为不同：9181 拦 / 9337 不拦）

本节为 2026-09-10 深夜修正版：早前发布的「9337 判定位漂移至 0x08」是错误归因——当时用「PM 后 md+8 是否变化（槽分配）」当 JIT 判据，实际上 md+8 变化只代表槽分配，JIT 与否要看 md+md8+8 是否出现真实函数头。

用 COMPLUS_ZapDisable=1（禁 NGEN，强制 IL-only，fresh 状态 md+8=0、+3=0x0B、b6=0x80 与 dump 完全同态）重跑后的修正结论：

场景 9181（A/B dump 实测） 9337（ZapDisable 实测）
0x80 不手术 + PrepareMethod 不 JIT（+3=0x0B、md+8 恒 0、CodeAddr 不可用） JIT（+3=0x3B、md+8 回填、md+md8+8=55-8B-EC-57）
0x20 手术 + PrepareMethod JIT（+3=0x39、md+8 回填） JIT

结论修正为：9181 的 PrepareMethodDesc 管线（Finalize 执行循环 gate 链）确实拦截 0x80 方法；9337 的同类管线不拦（0x80 也直接 JIT）。servicing 差异是「拦不拦」的行为差异，不是「判定位漂移」。9337 版本的 JIT 触发点不在我逆向到的 PrepareMethodDesc 主体内（该函数只有登记二分 + SetFlag6），具体实现在入口函数的前后段，待后续逆向。

另：9-4 旧文的 x64 结论（PrepareMethod 无条件 ForceJIT）与 9337 x86 行为同构——9337 代两个架构行为一致，9181 x86 的拦截是旧 servicing 特有行为。这也解释了 9-4 时「x64 手术在 BCL 扫描 0 命中」——x64 上不手术也 JIT，手术自然测不出差异。

附带方法论教训（写给自己）：跨进程验证 JIT 状态，唯一可信判据是 md + ReadInt32(md+8) + 8 处的字节内容；entry 指针是 PM 前缓存的 precode 地址，JIT 回填不反映在 precode 体，不能作为判据。

8.5 生产方案（x86 HookInfo 修复）

★ 顺序约束（关鍵）：手术必须发生在首次 PrepareMethod 之前——首次 PM 会把方法登记进 module 注册表，之后再 PM 走「已登记」分支（SetFlag6 + Register 直接返回），不会 JIT。9-4 版 HookInfo 的「先 PM 再手术再 PM」结构在 9181 上无效就是这个原因。

配套校验（防 servicing 静默失效）：PrepareMethod 后读 +3——0x0B→0x39（bit0 置位）且 md+md8+8 处出现 55 8B 函数头即成功；否则 fallback（precode patch / 激活时 hook）。注：9337+ 上不手术也 JIT（8.4），手术是无害冗余——两代 servicing 下这套代码都工作。
