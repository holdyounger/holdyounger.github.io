概述

整个系统的剪贴板突然无法读写，Set-Clipboard / Get-Clipboard 都报”所请求的剪贴板操作失败”。本文记录一次定位过程，并给出可复用的脚本，用于找出当前打开剪贴板而未关闭的进程。

相关说明

剪贴板是系统全局资源，同一时刻只能有一个窗口通过 OpenClipboard 打开它，必须配对 CloseClipboard 释放。某个程序打开后不关闭，其他程序就全部失败。

1. 现象

在 PowerShell 中执行以下命令，均报错：

报错信息为 ExternalException，文字为”所请求的剪贴板操作失败”。Set-Clipboard 耗时约 1.26 秒，说明 PowerShell 内部重试数次后才放弃。

读和写都失败，说明问题不在某次数据内容，而是剪贴板根本打不开，即 OpenClipboard 失败（CLIPBRD_E_CANT_OPEN）。

2. 排查思路

  1. 确认是否为全局占用：读、写均失败，基本可以排除单个数据格式的问题。
  2. 找出持有者：系统没有直接列出”谁持有剪贴板”的命令，但 user32 提供了 GetOpenClipboardWindow()，它返回当前打开剪贴板的窗口句柄。再用 GetWindowThreadProcessId() 把窗口反查到进程 ID。
  3. 判断是否假死：Get-Process 的 Responding 字段为 True 表示消息循环仍在工作，程序没有卡死，而是打开剪贴板后没有释放。

4. 实际定位结果

在卡顿期间运行脚本，输出如下：

Open clipboard window handle: 0x6E923E2
Id                     : 90076
ProcessName            : GameViewer
Responding             : True
Path                   : C:\Program Files\Netease\GameViewer\bin\GameViewer.exe

持有者为网易 GameViewer（远程控制/屏幕共享工具）。Responding: True 说明它没有假死，而是打开剪贴板后未释放。

5. 结论与处理

  • 本次根因：GameViewer 占用剪贴板未释放，导致系统级剪贴板不可用。这属于第三方程序的行为，不是系统故障。
  • 排除项：同期排查的 clipboard-spike（ClipSense）未出现在持有者中，与此次问题无关。两者属于不同问题，不要混为一谈。
  • 处理方式：退出 GameViewer（注意退出会断开正在进行的远程会话），然后重新执行 Set-Clipboard / Get-Clipboard 验证是否恢复。若不想退出，可以用 Stop-Process -Id <PID> 强制结束，但会丢失该程序的状态，应谨慎使用。

6. 通用经验

  1. 剪贴板”卡住”时，先用 GetOpenClipboardWindow 定位持有者，比重启资源管理器或系统更精确、代价更小。
  2. 持有者 Responding: True 说明是程序逻辑未释放资源，False 则更像程序假死。
  3. 排查时要区分”系统剪贴板被占用”与”应用内粘贴失效”两类问题，它们的报错和定位手段完全不同。
