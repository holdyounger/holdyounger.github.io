MethodDesc 手术与 PrecodeFixupThunk：.NET inline hook 取真实函数头的完整定性

场景：对一个 .NET Hook 框架做加固时发现，Marshal.GetFunctionPointerForDelegate 之外那条经典路径——RuntimeMethodHandle.GetFunctionPointer——对一部分方法返回的不是真实函数头，而是 E8 → clr.dll!PrecodeFixupThunk 的临时入口。inline hook 装在跳板上是装不住的。本文记录两轮运行时实证（x64/x86）+ 一轮静态取证如何把这个现象拆成三层、各自定案的完整过程。

版本锚定：实验运行时为 .NET Framework 4.8.4614（x64）/ 4.8.1（x86）；静态取证对象 clr.dll 4.8.9345.0（Win11 25H2 服务版，sha256 前缀 217a9b19…）。CLR 内部结构布局随 build 漂移，本文引用的 RVA/偏移仅对对应 build 有效。

一、现象：三类方法，三种入口形态

用 GetFunctionPointer 取一批 BCL 方法的入口时，按返回形态自然分成三类：

方法特征入口形态能否直接 hook
已 JIT 的普通方法E9 → 真实代码（回填后的 FixupPrecode）✅
未 JIT 的普通方法E8 → PrecodeFixupThunk（延迟绑定临时入口）❌ 跳板
带 0x80 标志的方法（继承/override 链）E8 → PrecodeFixupThunk，且 PrepareMethod 后可能仍停留 E8❌ 跳板

byte+6 = 0x80 是 MethodDesc（MD）里 RequiresInheritanceCheck 标志——继承/override 链上的方法（如 Process.StartWithShellExecuteEx、StartWithCreateProcess 这类自造 override 或 BCL 继承方法）普遍携带。

二、调度层定性：手术到底骗过了谁

「手术」是一组双位操作：临时把 MD 的 byte+6 从 0x80（RequiresInheritanceCheck）改为 0x20（mdcStatic，静态方法标志）——即「清继承检查 + 伪装静态」，调 GetFunctionPointer，拿到入口装完 hook 再立即还原原值。

2.1 IDA 逆向定位：谁在消费 0x20 位

对 clr.dll 4.8 x64 做逆向（带注释锚点），MD byte+6 的 0x20 位有四个消费点：

消费点地址（4.8 x64）行为
TryGetMultiCallableAddrOfCode0x18003de10(b6 & 7) == mcFCall 分类判定，决定走哪条取代码路径
MayHaveNativeCode 冷路径0x18040408ftest [rbx+6], 0x20 ← mdcStatic 命中点
MayBeRemotingIntercepted0x18003dd96开头即 test [rcx+6], 0x20 → return 0
IsVtableMethod 冷路径0x180108568同读 0x20 位

2.2 手术机制

  • 带 0x80 的方法，CLR 认为「可能还没到可以直接取代码的状态」，GetFunctionPointer 不走直达 native code 分支，停在 FixupPrecode 的 E8 阶段；
  • 设 0x20（mdcStatic）后，CLR 认为可以直达代码，配合 PrepareMethod 强制 JIT 回填，GetFunctionPointer 预期直通真实函数头。

第一层定性：手术改变的是 CLR 调度分支的判定输入，不是方法本身的行为——它骗的是「这个方法能不能直接给代码地址」这组判断（四个消费点全部看 byte+6）。

但「预期直通」这一步后来被实验证伪了一半——见下一节。

三、回填层定性：全量扫描证伪了手术的表面价值

拿到「手术有效」的印象后做了一次 BCL 全量扫描验证——结果反转：

两个关键反例：

  1. 无手术对照也回填了：StartWithShellExecuteEx（带 0x80）不做手术，单跑 PrepareMethod，入口就从 E8 变 E9 直达真实代码——手术对这批方法非必需；
  2. 0x20 位并不改变 entry 形态：对 StartWithCreateProcess 做手术+PrepareMethod，在 byte+6=0x20 期间调用 PrepareMethod 后，entry 仍是 E8→PrecodeFixupThunk（DumpState 在还原前调用，排除了「还原后才取值」的解释）——mdcStatic 位没有让 GetFunctionPointer 直通真实函数头；
  3. 手术救不了任何 still-thunk：剩下的 51 个方法手术后依旧 E8。检查它们的 md+8 字段发现两类形态——28 个正值（偏移落在似函数头），23 个负值（token 形态，跟随得到垃圾地址）。

第二层定性：这 51 个方法是 BY DESIGN——它们是 async/Task 基础设施生成的 IL stub / delegate 方法，md+8 编码的是 token 而非代码偏移，根本不是「没回填」，是「结构上没有常规 native code 槽」。

随之浮出的是全场最重要的结论：取真实函数头的普适方法不是任何手术或 PrepareMethod 组合，而是 md + ReadInt32(md+8) + 8 的偏移跟随——对任何形态都成立（正值偏移直达真实函数头；这正是未 JIT 方法 md+8 已预填「将要 JIT 的代码槽」偏移的原因）。Hook 框架初始化逻辑里按这个公式跟随，才是正解。

对手术价值的修正也在此定案：mdcStatic 位（0x20）的作用不是「让 GetFunctionPointer 返回真实函数头」（阶段3 反例已证伪），而是更可能与 PrepareMethod 在 0x80 方法上不完整 JIT/不回填 有关——即手术是给 PrepareMethod 扫清继承检查障碍，让 md+8 指向的代码槽真正被 JIT 回填。它的真实作用域在 BCL 离线扫描中未复现（0/2171），生产触发需 w3wp + 真实 IIS + 反射未初始化时序。

四、架构层定性：x86 上 PrepareMethod 根本不干活

第二个反转来自跨架构验证。拿一份 x86 进程的 dump 复核时发现，x86 上同一套「手术 + PrepareMethod」完全失效：

架构PrepareMethod 实现效果
x64（4.8.4614）PrepareMethodDesc → MethodCallGraphPreparer::Run真 ForceJIT，回填成立
x86（4.8.1）只登记，不 JIT空转，Not JITTED

x86 dump 里的 MD 特征自证了这一点：md+8 = 0——连代码槽都没分配，是「已登记未 JIT」分支的特征形态；而 byte+6 = 0x80 依旧在。

第三层定性：同一个 FCall 在两个架构上是两套实现语义。任何依赖「PrepareMethod 兜底强制回填」的跨架构 hook 框架，在 x86 上都是空中楼阁——x86 必须走真实调用触发 JIT（或偏移跟随预填槽）。

五、静态取证：为什么手术是被迫的（REA 证据）

用 REA 对 clr.dll（4.8.9345.0，x64）做静态取证，给「为什么必须做字段级手术」补上根因：

CLR 的方法调度内部 API 一个都不导出。托管代码侧唯一合法入口就是 RuntimeHelpers.PrepareMethod，而它恰好在上面两节里被证明「x86 空转、x64 也只覆盖部分场景」。所以字段级手术不是框架作者的偏好，是被 API 面逼出来的唯一手段。

附带一条工程警告：CLR 服务更新会使 RVA 全部漂移——早期记录的 clr.dll+0x18E5B0（PrecodeFixupThunk）在 4.8.9345.0 同 RVA 处已经是 xor rax,rax; ret。凡引用 CLR 内部地址，必须绑 build 号。

六、最终定性

层结论状态
调度层手术（清 0x80 + 设 0x20 mdcStatic）骗的是「可否直达代码」的分支判定输入（IDA 定位四个 0x20 消费点）；但 mdcStatic 不改变 entry 形态✅ 定案
回填层51 still-thunk BY DESIGN（IL stub，md+8=token）；普适解 = md+ReadInt32(md+8)+8 偏移跟随✅ 定案
架构层x64 PrepareMethod = ForceJIT；x86 = 只登记不 JIT，跨架构不可依赖✅ 定案

一句话定性：PrecodeFixupThunk 停留不是缺陷，是 CLR 延迟绑定 + 继承检查 + IL stub 三重设计的正常形态；「清 0x80 + 设 0x20」手术是窄域绕过（PrepareMethod 对 0x80 方法不回填的特定时序，BCL 离线扫描 0/2171 复现，生产触发需 w3wp + 真实 IIS + 反射未初始化时序），且 mdcStatic 位本身不改变 entry 形态——普适解是 md+8 偏移跟随。

工程实践清单

  1. hook 入口解析一律走 md + ReadInt32(md+8) + 8，不依赖 entry 形态判断；
  2. x64 可用 PrepareMethod 预热辅助回填，x86 不要依赖它；
  3. 手术保留为最后兜底（还原必须放 finally，崩溃现场要能自证未破坏 MD）；
  4. IL stub/delegate 方法（md+8 为 token 形态）直接放弃 inline hook，走重定向/表替换类方案；
  5. 所有 CLR 内部偏移按 build 号建档，服务更新后全量重校。

实证方法与取证细节：WinDbg + SOS（!dumpmd / !u / 内存直读 MD 字段）两轮运行时验证；REA v6.8.0 静态取证（导出表/符号/PE 身份）见 scripts/clr-precode-rea-20261104/。
