概述

IIS 网站点击无响应时，通过抓取 w3wp 进程 Full Dump，使用 WinDbg 分析线程池状态和线程栈，快速定位第三方模块阻塞等根因。

一、分析前准备

1.1 确认 Dump 类型

第一条必跑命令，自动分析异常类型。

重点确认：

  • 是否为 Full UserDump（只有 full dump 才能看完整堆栈）
  • 异常代码（0xc0000005 崩溃 / 0xc0000135 状态停留 / 无异常只是挂起）
  • Not Full UserDump → 换一个 full dump，否则栈信息不全

1.2 加载 Symbols

必加的私有符号：

  • IIS 模块：%WinDir%\System32\inetsrv
  • 你的 .NET 程序集 PDB
  • 第三方 DLL PDB（排查问题时往往关键）

二、线程池状态（第一步要看的）

典型输出解读

诊断要点：

指标含义提示
CPU 高 + Running 多代码死循环或锁竞争查 !runaway
CPU 低 + 全 busy线程在等外部资源重点查栈
Work Request in Queue > 0任务积压，无线程处理根因信号
Idle = 0 且全 busy线程池饱和看谁卡住了

黄金法则：低 CPU + 线程全 busy = 阻塞（等 DB、远程调用、文件锁），不是计算密集。

三、线程栈分析

3.1 快速全景：!stacks 2

高亮锁持有情况的彩色线程视图，能一眼看出死锁。

如果报错 Unable to get value of PsActiveProcessHead，说明内核符号未加载，跳过此步，用 ~* kb 手动查。

3.2 完整栈：~* kb 2000

Dump 所有线程的 Native 调用栈，每个线程逐一分析。

常用线程切换命令：

3.3 托管栈：!clrstack

对可疑线程同时跑 Native 栈（kb）和托管栈（!clrstack）。

四、关键分析维度

4.1 GC 和托管堆（.NET 应用）

常见问题特征：

  • GC 堆逼近上限 → 内存泄漏
  • 大量 HttpContext 滞留 → 请求队列阻塞
  • 数据库连接池耗尽，线程全挂等连接

4.2 同步锁分析

!stacks 2 彩色输出能直接看到哪个线程持有了哪个锁，一眼定位死锁。

4.3 句柄和资源泄漏

4.4 特殊等待：CLRSemaphore

信号量等待本身正常，但如果超时参数很大（00004e20 等），说明工作项没有正常入队。

五、常见无响应根因速查表

症状关键命令常见原因
CPU 100%，线程全 busy~*kb / !runaway代码死循环、同步锁竞争
CPU 低，线程全等外部资源!locks / !stacks 2等待 DB 连接、远程 API、文件锁
大量 HttpContext 对象!dumpheap -type HttpContext请求队列满，并发阻塞
GC 频繁，堆逼近上限!eeheap -gc内存泄漏、大对象未释放
Handle 持续增长!handle句柄泄漏（文件/进程/Event）
第三方 DLL 线程卡住~* kb + 模块名该 DLL 初始化/回调阻塞

6.3 结论

  • 该 DLL 不在 System32，可能是自研或第三方注入模块
