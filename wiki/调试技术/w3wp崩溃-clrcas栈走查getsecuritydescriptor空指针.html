概述

金蝶 K3Cloud 用户导出对账单 Excel 时 w3wp 崩溃（c0000005）。完整还原：FarPoint 控件许可证加载用 BinaryFormatter 反序列化 → 进程内 Hook 引擎的安全 Binder 拦截 → P/Invoke 配置检查 → 触发 CLR CAS 声明式权限栈走查 → clr!Assembly::GetSecurityDescriptor 解引用空指针。崩溃点在 CLR 内部（CLR bug），用 IDA 把 NULL 路径在汇编层钉死。

关键字：#调试技术/WinDbg 调试技术/dump 编程语言/dotnet/clr 逆向工程/ida iis/w3wp cas

一句话结论：金蝶 K3Cloud 用户导出对账单 Excel 时，FarPoint 控件许可证加载使用 BinaryFormatter 反序列化，进程内的反序列化防护 Hook（安全 Binder）拦截检查 → P/Invoke 配置检查 → 触发 CLR CAS 声明式权限栈走查 → CLR 内部 clr!Assembly::GetSecurityDescriptor 解引用空指针崩溃（c0000005）。崩溃点在 CLR 内部（CLR bug 性质），但触发链由 Hook 引入。不是攻击行为，是正常业务操作触发。

二、业务场景完整还原（自顶向下）

这是本次分析最有价值的部分——完整的用户操作 → 崩溃链路：

关键认知：

  1. 触发源是 GrapeCity/FarPoint 控件的许可证机制（license 数据用 BinaryFormatter 序列化，内含 Hashtable），不是攻击流量
  2. 进程内的反序列化防护 Hook 是挂给 BinaryFormatter 的安全 Binder，任何 BindToType 都会走配置检查——license 反序列化这种”无害绑定”也会进检查流程
  3. 白名单检查本身正是为了避免误报，但检查动作（P/Invoke）引发了崩溃

Module::FindDomainFile 的两条 NULL 路径（汇编钉死）

Module::FindDomainFile @ 0x18000e968：

两条 NULL 路径：

  1. 多域模式：该 Module 的域索引超出目标 AppDomain 的 assembly 列表长度，或列表槽位为空（该域中此程序集尚未注册 DomainFile）
  2. 单域模式：传入的 AppDomain ≠ Module 所属域 → 不查列表，直接返回 NULL（模块根本不在这个域里）

关于”两段重复 mscorlib 反射帧”的修正：托管栈参数出来后确认，这不是 Hook 重入——两段 RuntimeMethodHandle.InvokeMethod 分别是 ServiceFacade 反射调插件方法和 K3Cloud 服务框架外层反射调用，属于框架的正常反射模式。Hook 的 Binder 只进了一层（BindToType 一帧）。

修复建议（按优先级）

  1. Hook 引擎代码（根治）：配置检查的 P/Invoke 声明加 [SuppressUnmanagedCodeSecurity]，hook 引擎程序集标记 SecurityCritical / 授予完全信任 → 消除 DoDeclarativeActionsForPInvoke 声明式 demand 路径，走查不再发生
  2. 配置预载（更彻底）：启动时把 hook 配置预载到托管侧缓存（静态字典 / MMF），BindToType 回调内不再每次 P/Invoke
  3. 白名单短路（低成本止血）：mscorlib 等系统程序集 + System.Collections.Hashtable 这类 BCL 基础类型在托管侧直接放行，不进 native 检查（检测目标是业务类型反序列化，BCL 类型本就该放）
  4. 宿主侧：建议客户升级 .NET Framework 4.8 到最新 CU，修复 CLR 自身缺陷；升级前可用 IDA 对照新版 clr.dll 的 Assembly::GetSecurityDescriptor 是否已加判空
  5. 防重入加固（次要）：BindToType 处理期间避免再触发反射加载路径

AppDomain 观察

!threads 显示进程存在两个 AppDomain：

  • 默认域（多数线程）
  • 第二域（崩溃线程的多个对象、Hook Binder this 都在此地址段）

结合崩溃点 FindDomainFile 返回 NULL：CAS 走查回溯经过 P/Invoke ILStub 帧时，stub 所属程序集在其查找的 Domain 中无 DomainFile 绑定（域边界/动态 stub 交互问题）。进程内多 AppDomain（ASP.NET 域隔离）放大了此 CLR 缺陷的触发面。

给同类 Hook 引擎开发者的启示

  1. Binder 回调内避免 P/Invoke：BinaryFormatter 的 BindToType 回调发生在序列化管线深处，此处任何 P/Invoke 都会触发 StubHelpers.DemandPermission → 声明式 CAS 全栈走查（哪怕目标 native 函数无权限要求）——既可能踩 CLR 缺陷，也有性能损耗
  2. 配置预载：把检查所需数据在启动时预载到托管侧，回调内纯托管判定
  3. BCL 类型白名单前置：mscorlib 基础类型绑定在托管侧直接放行，不进 native 检查
  4. [SuppressUnmanagedCodeSecurity]：完全信任的 hook 引擎程序集可对 P/Invoke 声明此特性，整条绕开声明式 demand（需引擎自身代码可信）
