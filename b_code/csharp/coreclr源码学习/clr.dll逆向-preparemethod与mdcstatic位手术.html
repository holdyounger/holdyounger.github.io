clr.dll 逆向：PrepareMethod 与 mdcStatic 位手术

clr.dll 逆向：PrepareMethod 与 mdcStatic 位手术

Properties1
tagsdnet, clr, 逆向工程/ida, hook

2026年9月04日13分钟阅读

一句话结论

RuntimeHelpers.PrepareMethod 不读任何 m_invocationFlags（无条件强制 JIT）；HookInfo 的「清 0x80 设 0x20(mdcStatic)」位手术影响的是 CLR 原生侧 TryGetMultiCallableAddrOfCode/MayHaveNativeCode/MayBeRemotingIntercepted 对 MethodDesc+6 字节的判定分支；取真实函数头靠 md + ReadInt32(md+8) + 8 偏移跟随，不靠手术。手术在纯 BCL 扫描中未复现到”有效”实锤（0/51），其必要场景推测需真实 IIS 生产环境时序。

关联文章：clr.dll逆向-GetFunctionPointer与Precode（GetFunctionPointer 决策链与 Precode 体系）

一、分析背景

某个 .NET Hook 框架的初始化组件（下文统称 HookInfo）在 x64 分支有一段位手术：PrepareOldMethodForHook：

本次分析回答三个问题：

  1. PrepareMethod 是否通过 m_invocationFlags 判断是否执行？（答：否）
  2. GetInvocationFlags 能否改为属性访问？（答：读可以，写不行）
  3. 当年加 mdcStatic 到底为什么？（答：见第四节，复现后修正）

二、CLR 逆向结论（clr.dll 4.8.4795 x64，IDA 已加 22 条注释）

2.1 PrepareMethod（FCall，0x18065eca0）—— 与 InvocationFlags 无关

ReflectionInvocation::PrepareMethod(ReflectMethodObject*, inst, count)
  ├─ GetAttrs() & 0x400 (abstract) → 抛 Argument_CannotPrepareAbstract
  ├─ CheckRestore / 泛型 instantiation 校验 / FindOrCreateAssociatedMethodDesc
  └─ PrepareMethodDesc(md, ...)
        └─ MethodCallGraphPreparer::Run()   ← CER 准备 + IL 调用图遍历
  • 全程不读 mscorlib 侧 m_invocationFlags —— 那是托管对象（RuntimeMethodInfo）上的字段，native FCall 只持有 MethodDesc*，物理上无法读到
  • 无条件执行（内部 CER 检查去重），不存在”根据 InvocationFlags 跳过”的分支

2.2 m_invocationFlags 是纯托管概念

侧位置作用
mscorlib 托管RuntimeMethodInfo.m_invocationFlags 字段MethodInfo.Invoke 的准入校验缓存（NoInvoke/ContainsStackPointers → 抛异常）
clr.dll 原生不存在grep 全部 VM 代码零命中

托管 get_InvocationFlags IL 结构（net48 实测反汇编）：读 m_invocationFlags 字段 → 测 INITIALIZED 位 → 未初始化则懒计算（GetSecurityFlags + 逐位 OR）→ 写回缓存。消费者：InvokeArgumentsCheck/UnsafeInvoke/RuntimeConstructorInfo。与 JIT 准备无关。

2.3 真正消费 MethodDesc+6 字节的函数（★ = 手术影响点）

函数地址读取点作用
TryGetMultiCallableAddrOfCode0x18003de10(b6 & 7) == 1 分类位；b[3]&1 HasStableEntryPointGetFunctionPointer 返回真代码 vs precode 的核心决策
MayHaveNativeCode0x180010b70（冷路径 0x18040408f）★test [rbx+6], 0x20mdcStatic 位参与”可直达 native code”判定
MayBeRemotingIntercepted0x18003dd90开头即 test [rcx+6], 0x20 → return 0mdcStatic 短路 remoting 拦截
IsVtableMethod0x1800070c0（冷路径 0x180108568）同读 0x20 与 0x80虚表判定

IDA 中已按 [HookInfo 分析] 前缀添加注释（11 处函数级 + 11 处函数内关键指令），Ctrl+F 可搜。

2.4 TryGetMultiCallableAddrOfCode 完整决策树（0x18003de10）

GetFunctionPointer() → QCall RuntimeMethodHandle::GetFunctionPointer（0x180066080）→ 本函数。入参 accessFlags（GetFunctionPointer 传 CORINFO_ACCESS_UNMANAGED_CALLER_MAYBE|LDFTN=16，v5 = a2 & 1 即 UNMANAGED_CALLER 位）。

决策顺序（每条分支 = 一种方法形态拿 entrypoint 的方式）：

TryGetMultiCallableAddrOfCode(md, accessFlags)
│
├─① IsGenericMethodDefinition(md)          → 抛 InvalidOperationException（未实例化泛型不可调）
│
├─② IsWrapperStub(md) || IsEnCAddedMethod(md)
│      → GetOrCreatePrecode() → GetMethodEntryPoint()
│      【wrapper stub（unboxing/实例化 stub）与 EnC 新增方法：先确保有 precode，返回稳定入口】
│
├─③ accessFlags 无 UNMANAGED_CALLER 且 IsRemotingInterceptedViaVirtualDispatch(md)
│      → CRemotingServices::GetNonVirtualEntryPointForVirtualMethod(md)
│      【Remoting 拦截：虚分发被拦截的虚方法，返回非虚入口点（remoting 桩）】
│
├─④ Module::IsEditAndContinueEnabled(md 的模块)
│      → GetOrCreatePrecode() → GetMethodEntryPoint()
│      【EnC 启用的模块：必须用可回 patch 的 precode 入口，保证热更新时可改写】
│
├─⑤ (b6 & 7) == mcFCall(1)  ←★ byte+6 分类位（HookInfo WriteByte 影响的判定之一）
│      且 非remoting拦截 且 MethodTable 无 (0xF0000)==0xC0000（?）且 (MT & 0x20000000)==0
│      → ECall::GetFCallImpl(md)                ← 直接返回 FCall 的原生实现地址！
│        （GetFCallImpl 失败 → GetOrCreatePrecode）
│      【FCall 方法：绕过 precode 直达 ECall 表里的 C++ 实现】
│
├─⑥ 否则 IsPointingToNativeCode(md)          ← 读 b[3]&1(HasStableEntryPoint) 与 b[3]&2(HasNativeCodeSlot)
│      → GetNativeCode(md)                     ← 直接返回已 JIT 的真实代码
│      【★ 最理想分支：已 JIT 且无 precode 间接，entry == realCode】
│
├─⑦ b[3]&1 HasStableEntryPoint
│      → GetMethodEntryPoint(md)               ← 返回方法当前入口（可能是 precode）
│      【已 JIT 但仍带 precode 的方法（如需 backpatch 的场景）】
│
├─⑧ MayHaveNativeCode(md)==0 或 IsRemotingInterceptedViaPrestub(md)
│      → GetOrCreatePrecode(md)
│      【★ MayHaveNativeCode 读 byte+6 的 0x20(mdcStatic)——HookInfo 手术的机制命中点。
│         判定失败 = 该方法"不可能有 native code"→ 只能给 precode（Hook 拿不到真实函数头的根因之一）】
│
└─⑨ md 所在 chunk 的 word >= 0（a1[-8*chunkIndex-6]）
       → GetTemporaryEntryPoint(md)            ← 临时入口点（PrecodeFixupThunk 场景）
   否则 → return NULL

2.5 各被调函数语义（clr.dll 实测反编译）

函数地址功能
IsGenericMethodDefinition0x18000e19c是否泛型方法定义（未实例化）。是 → 直接抛 InvalidOperationException， Hook 不能挂未实例化泛型
IsWrapperStub0x180029228是否 unboxing stub 或 instantiating stub（泛型包装桩）。这类方法的”入口”语义是桩本身，须先 GetOrCreatePrecode
IsEnCAddedMethod0x18002ad0c是否 EnC（Edit and Continue）运行期新增方法
IsRemotingInterceptedViaVirtualDispatch0x18003dd64MayBeRemotingIntercepted && IsVtableMethod——remoting 透明代理场景的虚方法拦截
IsRemotingInterceptedViaPrestub0x18001123cMayBeRemotingIntercepted && !IsVtableMethod && !RequiresInstArg —— 非虚方法的 remoting 拦截走 prestub
MayBeRemotingIntercepted0x18003dd90开头 test [rcx+6],0x20（mdcStatic）→ 静态方法直接 return 0；再排除 MT flags 0xE0000==0x20000（context-bound?）及 Object ctor/finalizer
IsPointingToNativeCode0x18003df00读 b[3]&1（HasStableEntryPoint）+ b[3]&2（HasNativeCodeSlot）+ Precode::IsPointingTo(entry, nativeCode)——判断 entry 是否已指向真实 JIT 代码
MayHaveNativeCode0x180010b70综合分类位 + MT flags（0xF0000==0xC0000 即 COM? / 0x80000030）+ byte+6 的 0x20 位，判定”此方法可能存在 native code”。失败 → GetOrCreatePrecode（Hook 拿不到函数头的根因场景）
IsRemotingInterceptedViaPrestub0x18001123c见上 MayBeRemotingIntercepted
GetNativeCode0x1800103dc读 b[3]&8（HasNativeCodeSlot）→ 按 s_ClassificationSizeTable[分类] 定位代码槽指针，& ~1（bit0 是标志位）。无 native code slot 返回 0
GetMethodEntryPoint0x180006c78读方法当前入口点槽：有 native code slot（b[3]&8）走 ClassificationSizeTable 定位；否则从 MethodTable slot / chunk 间接解析。返回的可能是 precode 或真实代码
GetTemporaryEntryPoint0x18001df40沿 MethodDescChunk 的 TempEntryPoints 表找/分配临时入口（PrecodeFixupThunk 形态的来源之一）。GetOrCreatePrecode 内部也依赖它
GetOrCreatePrecode0x1801736dc有 TempEntry 就地升级为 precode（AllocMemTracker 分配），否则新分配 Precode（StubPrecode/FixupPrecode）并回填 entrypoint
ECall::GetFCallImpl0x180011578查 ECall 表拿 FCall 的 C++ 实现地址（Console.WriteLine、String.Compare 这类内部方法不走 JIT）
CRemotingServices::GetNonVirtualEntryPointForVirtualMethod0x18003e364remoting 场景：虚方法被透明代理拦截时返回非虚入口
IBCLogger::LogMethodDescAccessStatic（多处）IBC（Incremental Build Compatibility）日志探针，retail 关闭，无功能影响

一句话总结分支语义：

  • ⑤ FCall → 直达 C++ 实现
  • ⑥ 已 JIT 无 precode → 直达 native code（Hook 最理想）
  • ⑦ 已 JIT 有 precode → 稳定入口（可能 E8/E9 跳板，需 HookInfo 的 md+8 跟随）
  • ⑧⑨ 未 JIT / 异常场景 → precode / 临时入口（Hook 不能直接 patch 这里）

2.6 byte+6 位语义（net48 x64 实测）

位含义实测佐证
& 7分类（mcIL=0/mcFCall=1/mcPInvoke=2/mcEEImpl=3/mcArray=4/mcInstantiated=5/mcDynamic=7）String.ToUpper=0x08（mcIL+HasNonVtableSlot）
0x08mdcHasNonVtableSlot实例方法 0x08、静态方法 0x28
0x20mdcStatic（静态缓存位）IsNullOrEmpty(静态)=0x28、ToUpper(实例)=0x08；MayBeRemotingIntercepted 读此位

CoreCLR 现代源码（method.hpp）中对应的是 mdfStatic = 0x0080（16 位 m_wFlags），布局已完全重构 —— 不能拿新源码套 net48 x64 的字节偏移。

三、md+8 语义与真实函数头获取（复现定案）

3.1 md+8（int32）= 真实 JIT 代码相对 MethodDesc 的偏移

realCode = md + ReadInt32(md+8) + 8

实测（ReproMd8Probe）：StartWithShellExecuteEx md+8=0x82FEE0，md+0x82FEE0+8 = 0x7FF9A2F96A50 → 55 41 56 57（真实函数头）✓

HookInfo.Initialize() 的 E9/E8 跟随逻辑就是这个：Value = ReadInt32(md+8); Value = md + Value + 8，任何入口形态下都能拿到真实代码。

3.2 PrepareMethod 前后 entry 对比（无手术对照）

阶段entry形态
反射刚拿到（未 JIT）0x7FF94A550718E8 93 DE 7C 5F → clr.dll+0x18E5B0（PrecodeFixupThunk）
GetParameters 后同上无变化
PrepareMethod 后0x7FF94A44D080E9 63 C9 EF FF → 0x7FF94A44D080，bytes=48 83 EC 28 真实函数头

普通 PrepareMethod 就能让 entry 从 E8 回填成 E9 直达真实代码 —— 手术对这批样本非必需。

3.3 E8 跳板目标 = PrecodeFixupThunk

entry+5+rel32 = clr.dll+0x18E5B0（共享 PrecodeFixupThunk，所有未 JIT 方法指向同一地址）。GetJitFunPtrStatus 的 Injected 判定（b1 == 0xe9 || 0xe8）捕捉的就是这种形态。

4.1 广撒网扫描（ReproSurgeryHunter，21128 个 BCL 方法）

指标数值

手术在纯 BCL 环境未复现到”有效”场景。 仍 thunk 的方法全是 async/Task/IO 类（Stream.ReadAsync、TaskAwaiter.OnCompleted、CancellationToken.Equals…），by design（IL stub/delegate，md+8 编码 token 非偏移），手术天然无效。

4.2 md+8 两分类（仍 thunk 方法）

类别md+8 特征HookInfo 跟随落点占比
正值偏移~0xBC4E60（~12MB）0x7FF9A6BB****，bytes[0]=48/57 函数头形态 ✓28
负值 token0x9101B44D 等（高位 1）0x7FF9370D**** 垃圾23

→ HookInfo 的 md+md8+8 跟随对正值 md+8 有效，负值（token 类）落垃圾。

4.3 触发条件的真实语义

nOffsetPre8 < 0xFF（有符号 int32 比较）：

  • Process.Start md+8=0xA2F97230 → 负数 → 恒 < 0xFF → 手术触发 ✓（此时方法已 JIT，entry=真实函数头，手术前后无变化）
  • StartWithShellExecuteEx md+8=0x82FEE0 → 正数且 ≥ 0xFF → 不触发
  • 未 JIT 方法 md+8 是小 offset（如 ReproDerived.Compute md+8=0）→ 触发检查

4.4 实验环境注意

  • WSL interop 会把 32 位 exe 拉成 64 位宿主 → x86 验证必须 Windows 侧 run-net48-x86.bat
  • x86 进程下手术分支不走（!Is64BitProcess 只裸 PrepareMethod）；x86 的 md+8 是 m_codeOrIL 指针（大值）
  • MEMORY_BASIC_INFORMATION x64 布局：RegionSize 必须 UIntPtr 且 8 字节对齐（+24），否则 VirtualQuery 全误判

五、当年为什么加 mdcStatic —— 最终结论

综合 IDA 逆向 + 三轮复现：

  1. 不是”PrepareMethod 通过 m_invocationFlags 判断是否执行”——PrepareMethod 无条件执行
  2. 不是”让 GetFunctionPointer 返回真实函数头”——普通 PrepareMethod 就能回填（E8→E9），且手术在 BCL 扫描 0 命中
  3. 真实作用域（收窄后的推断）：针对「PrepareMethod 对带 0x80 方法失效的特定子集」——0x80 位使 CLR 在 CER/调用图准备阶段走继承检查路径，某些场景（继承检查失败/异常）导致代码槽未回填。手术 = 临时伪装”静态+无继承检查”绕过该路径，让 PrepareMethod 的 JIT 回填生效
  4. 生产取头路径：Initialize() 的 md + ReadInt32(md+8) + 8 偏移跟随才是主力，手术只是辅助

未实锤的残留：生产 w3wp + 真实 IIS 环境的反射初始化时序下，可能存在 BCL 扫描踩不到的手术必要场景。可结合生产日志中 JIT 回填失败的上报集中在哪些方法，对齐后做定向 A/B。
