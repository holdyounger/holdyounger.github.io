概述：Detours 的说明和简单使用

Detours

Detours 是微软提供的一套工具，主要用于win32 API的拦截

Github：microsoft/Detours: Detours is a software package for monitoring and instrumenting API calls on Windows. It is distributed in source code form.

仓库中有挺多示例程序可供参考。

使用 Detours 的大致流程：

在 Detours 的工作过程中，DetourTransactionBegin 函数首先用于启动一个截获（Hook）或解除截获（UnHook）的过程，这个过程中可能包含对多个函数的修改。然后，开发者可以使用 DetourAttach 或 DetourAttachEx 函数将 Detour 钩子附加到目标函数上，或使用 DetourDetach 函数将钩子从目标函数中分离出来。

相关函数说明

DetourAttach 函数说明

DetourAttach 是最常用的附加函数，将 Detour 钩子附加到目标函数上。

  • ppPointer：传入时指向目标函数原地址，成功后会被修改为指向 trampoline（跳板代码），可在 Detour 函数中通过它调用原始函数
  • pDetour：你的 Hook 函数地址，签名必须与目标函数一致
  • 返回值：NO_ERROR 表示成功

⚠️ DetourAttach 内部使用默认参数（5 字节跳转），对大多数 x86/x64 函数已足够。

DetourAttachEx 函数说明

DetourAttachEx 是 DetourAttach 的扩展版本，提供了对 Hook 过程更精细的控制，允许获取额外的诊断信息和控制桩（stub）的大小。

  1. ppRealTrampoline 指向可执行内存：该地址可以直接被调用（call），但不应被修改或释放——Detours 在 DetourDetach 时会自动处理
  2. ppRealTarget 不等于 ppPointer 修改后的值：ppRealTarget 始终是原始函数入口地址，而 ppPointer 被修改后指向 trampoline 代码块。调用 trampoline（通过 ppPointer）等效于调用原始函数，但 trampoline 可能包含额外的指令修复
  3. 所有扩展参数都可以传 NULL：如果你不需要某个输出参数，传 NULL 即可，功能退化为 DetourAttach
  4. 线程安全：与 DetourAttach 一样，必须在事务内调用

DetourUpdateThread 函数说明

DetourUpdateThread 函数是 Detours 库中的一个重要函数，用于在 Detour 事务处理过程中将特定的线程列入更新范围。Detours 是一个用于在运行时修改二进制代码（如函数钩子）的库，它允许开发者在不修改原始代码的情况下，拦截和修改函数的执行流程。

DetourUpdateThread 函数的作用是在这个事务过程中，将一个或多个线程列入需要更新的范围。这是因为在多线程环境中，直接修改函数的代码可能会导致竞态条件，即一个线程正在执行原始代码时，另一个线程可能已经修改了该代码。通过 DetourUpdateThread 将线程列入更新范围，Detours 库可以确保在事务提交时，所有相关线程的代码都被正确地更新，从而避免竞态条件。

具体来说，DetourUpdateThread 函数的作用是：

  1. 将指定的线程加入到 Detour 事务的更新列表中。
  2. 在事务提交时，Detours 库会遍历这个更新列表，并对列表中的每个线程执行必要的代码更新操作。

需要注意的是，在调用 DetourTransactionCommit 或 DetourTransactionCommitEx 函数提交事务之前，所有的附加、分离和线程更新操作都不会生效。一旦事务被提交，所有的修改就会立即生效，所有相关线程的代码都会被更新以反映这些修改。

因此，DetourUpdateThread 函数是 Detours 库中用于确保多线程环境下代码修改一致性和安全性的重要工具之一。

Detours 原理深入剖析

以上部分讲的是 Detours 的「怎么用」，这部分深入讲它的「内部原理」：
整体拦截架构、_DETOUR_TRAMPOLINE 结构体、以及它是如何保证原子性的。
以下内容基于 microsoft/Detours 的 detours.cpp / detours.h 源码（本地仓库 Windows-API-Usage\Windows\DetourDemo\Detours 内即为完整源码）。

一、Detours 的整体拦截架构

Detours 的核心思想非常朴素，只有三步：

  1. 覆盖：把目标函数 pbTarget 开头的几条指令（cbRestore 字节，至少 5 字节）改写成一个跳转指令，跳向我们的 Detour 函数。
  2. 搬家：把被覆盖掉的原始指令「搬」到动态分配的一块可执行内存里（trampoline），并在后面补一条跳转跳回原函数的剩余部分 pbRemain。
  3. 中转：把用户持有的原函数指针 *ppPointer 改写为指向 trampoline，这样用户在 Detour 函数里调用「原函数」时，实际执行的是 trampoline 里的那几条被搬走的指令 + 跳回剩余部分。

关键点：原函数代码段并不是整体被替换，只是开头 cbRestore 字节被一条跳转覆盖，其余指令仍在原处（pbRemain）。这保证了对函数主体几乎零侵入。

二、_DETOUR_TRAMPOLINE 结构体详解

_DETOUR_TRAMPOLINE 是 Detours 最核心的数据结构，它描述了一块 trampoline 内存：既保存了被搬走的原始指令，又保存了原始指令的备份（用于撤销 Hook 时恢复），还记录了指令对齐信息。

⚠️ 该结构体在 detours.h 中是**不透明（opaque）**的（只声明 typedef struct _DETOUR_TRAMPOLINE DETOUR_TRAMPOLINE, *PDETOUR_TRAMPOLINE;），真正的定义在 detours.cpp 内部。不同架构定义不同，下面给出最常见的 x86 和 x64 两个版本。

字段 作用

rbCodeIn[8]（仅 x64） x64 特有的 jmp [pbDetour] 间接跳转。因为 x64 的 jmp rel32 只有 ±2GB 范围，无法保证目标函数和 Detour 函数都在范围内，所以先用 FF 25 间接跳转（通过 pbDetour 这个 8 字节地址槽）跳到 Detour。

为什么 x64 需要 rbCodeIn（间接跳转）？
x86 的 E9 jmp +imm32 即可到达 32 位地址空间任意位置；而 x64 的 E9 相对跳转只有 ±2GB。Detours 无法保证 Detour 函数一定在目标函数 ±2GB 内，所以在 x64 下：

  • 原函数入口处写入的是一条 jmp [rip+disp]（FF 25）间接跳转，间接目标就是 trampoline 里的 pbDetour 指针槽（即 rbCodeIn）。
  • 写入的这 14 字节（FF 25 + 4 字节偏移 + 8 字节地址槽）覆盖了原函数开头。
  • rbCodeIn 这块「跳板地址槽」位于 trampoline 内，随 trampoline 一起分配在目标函数 ±2GB 范围内。

三、如何保证原子性（Atomicity）

「原子性」在 Detours 里有两层含义：① Hook 操作的原子性（事务机制）；② 单条跳转写入的原子性（不产生半改写指令）。下面分别说明。

3.1 单条跳转写入的原子性 —— 一次内存写完成跳转

修改目标函数代码时，最危险的是：另一个线程正在执行原函数，而我们在改写它的代码，导致线程执行到「写了一半」的指令。Detours 的解决思路是只做一条内存写就完成跳转安装：

  • x86：在目标函数入口写入一条 5 字节的 E9 jmp +imm32。CPU 保证对齐的 4 字节写是原子的，且整个跳转是通过「先写 jmp 那 1 字节（0xE9），再写 4 字节偏移」或整体写入完成的——DetourTransactionCommit 里 detour_gen_jmp_immediate 直接把整条指令写入。
  • 配合线程挂起 + EIP 重映射（见 3.2），保证没有线程卡在「半条指令」上。

实际上 Detours 更核心的原子性保障来自事务 + 挂起线程 + 指令重映射的组合，而不是依赖单条指令的原子写。因为只要有一个线程正停在要被覆盖的指令中间，即使单条写入是原子的，那个线程的后续执行也会错乱。

3.2 事务机制（Transaction）—— 整体原子性

这是「如何保证原子性」的主角。Detours 用「事务」把一组 Hook/UnHook 操作打包成要么全部成功、要么全部回滚的原子单位。核心流程：

为什么需要「挂起线程 + 指令重映射」？

因为改代码时，可能有一个线程正停在即将被覆盖的指令处。如果只改代码不处理线程，该线程恢复后会继续执行已被覆盖的区域，必然出错。Detours 的做法：

  1. DetourUpdateThread 在 Commit 前把相关线程挂起（SuspendThread）。
  2. Commit 时通过 GetThreadContext 拿到每个挂起线程的 EIP/RIP。
  3. 如果该 EIP/RIP 落在 pbTarget .. pbTarget+cbRestore（被覆盖区），就用 rAlign 对齐表把它重映射到 trampoline 里对应的位置（cxt.DETOURS_EIP = pTrampoline + detour_align_from_target(...)）。
  4. SetThreadContext 写回，这样线程恢复后实际执行的是 trampoline 里被搬走的等价指令，语义完全一致。

指令边界问题的根源：cbRestore 是「至少能放下一条跳转的整指令数」。DetourCopyInstruction 会一条一条完整复制指令，保证 cbRestore 一定是完整指令边界（不会把一条指令劈成两半）。同时 rAlign 记录每条指令原偏移→trampoline偏移的对应，使 EIP 重映射精确到「同一条指令」。

为什么要 FlushInstructionCache？

x86/x64 的 CPU 有指令缓存（I-Cache）和分支预测。代码被改写后，缓存里可能还是旧指令。FlushInstructionCache 强制刷新，确保后续执行取到新指令。

页面保护（VirtualProtect）的作用

目标函数所在的页原本可能只是 PAGE_EXECUTE_READ（只读）。写代码前需要先 VirtualProtect(..., PAGE_EXECUTE_READWRITE, &dwOld) 临时放开写权限，写完再 VirtualProtect(..., o->dwPerm) 还原成原来的保护属性。这既满足改写需要，又不永久放宽页面权限（安全）。

Detours 还维护自己的 trampoline 内存池（region）：

  • detour_alloc_trampoline 在目标函数 ±2GB 范围内找一块 64KB 对齐的空闲内存页作为 region（因为跳转/访问受 ±2GB 范围限制）。
  • 一个 region（DETOUR_REGION_SIZE=0x10000）被切成若干 trampoline 块，用 pFree 空闲链表管理。
  • trampoline 页平时设为 PAGE_EXECUTE_READ，仅在写时临时放开（detour_writable_trampoline_regions/detour_runnable_trampoline_regions）。

3.3 失败回滚（Abort / 部分失败）

事务还保证回滚：

  • DetourTransactionAbort() 手动中止：遍历已记录的操作，把已写回的目标代码还原（或释放已分配的 trampoline），恢复页面保护，恢复线程。
  • 任一步失败（s_nPendingError != NO_ERROR）时，后续操作直接短路返回错误，Commit 会走到 DetourTransactionAbort 清理现场，避免留下半 Hook 状态。

③ 遍历挂起线程：EIP/RIP 重映射

这一步处理「改写代码时正巧有线程执行到被覆盖区」的竞态：

  • 安装时：若线程的 EIP/RIP 落在 pbTarget..pbTarget+cbRestore（即将被覆盖的指令区），用 rAlign 对齐表把它映射到 trampoline 里同一条指令的等价位置，SetThreadContext 写回，线程恢复后继续执行语义完全一致的搬移指令。
  • 卸载时：反向——线程若停在 trampoline 内，映射回原函数对应指令位置。

detour_align_from_target / detour_align_from_trampoline 就是查 _DETOUR_TRAMPOLINE.rAlign[] 这张「原偏移 ↔ trampoline 偏移」对照表，保证重映射精确到同一条指令（不劈半）。

④ 恢复页面保护 + 刷新指令缓存 + 收尾

收尾四件事：

  1. 还原页面保护：改代码前用 VirtualProtect(..., PAGE_EXECUTE_READWRITE) 临时放开写权限，Commit 后 VirtualProtect(..., dwPerm) 还原成只读可执行，避免永久放宽页面权限（安全）。
  2. FlushInstructionCache：x86/x64 有指令缓存，改写后必须刷新，否则 CPU 可能继续执行缓存的旧指令。
  3. 归还 trampoline：卸载（Detach）时把 trampoline 块归还空闲链表，若整个 region 空了且不保留，则 detour_free_unused_trampoline_regions 释放整块 region。
  4. ResumeThread 恢复所有被 DetourUpdateThread 挂起的线程。

三点六、trampoline（跳板）是怎么创建出来的

Commit 里反复用到的 rbCode、rbRestore、rAlign、pbRemain 这些字段，在 DetourAttachEx 的 detour_finish_attach 阶段就已填充好。这里把「创建跳板」的完整过程串起来。

① 在目标函数 ±2GB 内分配内存（detour_alloc_trampoline）

  • 一个 region = DETOUR_REGION_SIZE（0x10000，64KB），在目标函数 ±2GB 内找一块空闲内存页分配。
  • region 被切成 DETOUR_TRAMPOLINES_PER_REGION 个 trampoline 块，用 pFree 空闲链表管理（DetourRegion.pFree 指回下一个空闲块，块与块通过 pbRemain 字段串起来，形成嵌入式空闲链表）。
  • trampoline 页平时设为 PAGE_EXECUTE_READ，仅写时临时放开，写回后收紧（detour_writable/runnable_trampoline_regions）。

② 逐条搬移原指令（DetourCopyInstruction）

创建跳板的核心逻辑：

  1. DetourCopyInstruction 逐条解码原函数开头指令，原样复制进 rbCode，且保证完整指令边界（绝不劈半）。
  2. 至少复制 SIZE_OF_JMP（5 字节），否则放不下跳转指令，复制不足会返回 ERROR_INVALID_BLOCK。
  3. 搬移中做重定位：原指令里若有相对跳转/访问（call rel32 等），DetourCopyInstruction 会修正偏移，因为指令从原地址搬到了 trampoline，相对距离变了。
  4. 记录 rAlign 对齐表：每条指令的「原偏移 → trampoline 偏移」，这是第 ③ 步 EIP 重映射的依据。
  5. 备份原始指令到 rbRestore：这是 Detach 时 CopyMemory(pbTarget, rbRestore, cbRestore) 写回原函数的「原材料」，实现完美还原。
  6. 末尾补 jmp [pbRemain]：trampoline 执行完搬走的指令后，跳回原函数剩余部分继续执行。
  7. 记录 pbRemain（剩余代码起点）、pbDetour（Detour 函数入口）。

四、什么时候需要事务？（与上文的呼应）

上文提到「单个 DetourDetach 不需要事务」，这里补充底层原因：单个 Detach 本质上就是对目标代码一条原子写（写回 rbRestore）+ 释放 trampoline，不涉及多操作的协调；而只要涉及多个函数的 Hook/UnHook，就必须用事务保证它们要么一起生效、要么一起回滚，否则会出现「A 已 Hook、B 失败」的中间态。

实践建议：

  • 单函数单次 Hook/UnHook → 可以直接 DetourAttach/DetourDetach（内部仍是事务 API 的最小用法）。
  • 多函数、多步骤、需要回滚 → 必须 Begin/Commit/Abort 包裹，并配 DetourUpdateThread。

更严谨的说法：Detours 的 DetourAttach/DetourDetach 本质上都要求在事务内调用（源码里会检查 s_nPendingThreadId，不在事务内会返回 ERROR_INVALID_OPERATION）。所谓的「单个不需要事务」，是指「不需要额外自己包一层多操作事务」，Detours 内部依然用事务 API 完成单点写入。
